# 리뷰 처분 규칙

리뷰어 서브에이전트(`code-reviewer`·`security-reviewer`·`prompt-reviewer`·`plan-reviewer` 등)가 반환한 지적에 대해 메인 에이전트가 **수용/기각/유보** 중 어느 처분을 내릴지 판단하고, 그 결과를 **사유 1줄과 함께** 명시적으로 기록한다. 임의 선택을 막아 메인의 bias를 표면화시키는 것이 목적이다.

## 적용 트리거

리뷰어 에이전트의 결과를 받은 직후, 그 결과를 처리(코드 수정·기각·다음 단계 진행)하기 **전**에 본 규칙을 적용한다.

- **Do:** 리뷰어가 severity 무관 지적을 **1건이라도** 반환했을 때 항상 적용
- **Don't:** 단일 ✅(이슈 0건)만 반환된 경우는 적용 면제 — 처분할 대상이 없음

## 처분 분류 (3택)

| 처분 | 의미 |
|------|------|
| **수용** | 지적대로 코드·문서를 수정한다 (또는 즉시 수정함) |
| **기각** | 지적이 부적절·오탐·맥락 무시라 판단하여 수정하지 않는다 |
| **유보** | 타당하나 현 작업 범위 밖. 별도 태스크·이슈로 분리 |

## 수용여부 판단 기준 (prompt-reviewer 결과 전용)

본 섹션은 **`prompt-reviewer` 결과 처분에만** 적용한다. `security-reviewer`·`code-reviewer`·`plan-reviewer` 등 다른 리뷰어 결과에는 적용하지 않는다 — 그쪽은 보안 결함·코드 품질·계획 결함이라 simplicity first보다 결함 해소가 우선이다.

`prompt-reviewer` 지적은 권고 자체가 결함을 elaborate 방향으로 풀어내는 편향이 있다. 메인이 무비판 수용하면 지시문 본문이 비대해지므로 다음 두 기준으로 **기각** 후보부터 먼저 거른다.

- **기준 1 (상식 축):** 지적이 요구하는 보강이 "LLM 상식으로 모호성을 충분히 없앨 수 있는" 수준이면 **기각**. 예: 일반적인 키워드 풀 명시, 자명한 단위 표기(라인 vs 토큰), 일반 보안 시멘틱 어휘 나열, 자연어로 이미 의미가 잡히는 표현의 형식화.
- **이유 1:** Claude 문서 작성의 cardinal rule인 **simplicity first** 위반. 지시문이 길어질수록 메인의 추론 부담·토큰 비용이 커지고, 명시성 ↑ 대신 LLM 상식 활용 ↓의 트레이드오프가 발생한다.
- **기준 2 (효과 축):** 문구를 추가한다고 메인의 실행 결과가 추가 전과 사실상 달라지지 않을 것으로 예상되면 **기각**. 예: 이미 자연어로 의미가 잡힌 표현에 "더 명확한" 재진술 추가, paranoid Don't 한 줄, 중복 cross-reference, 같은 결정으로 수렴할 게 뻔한 분기 명시.
- **이유 2:** 효과 0의 보강은 비용만 누적. 두 기준 어느 쪽이든 걸리면 기각 후보다.
- **반대 케이스 (수용):** 절차적 결함(예: 평가 순서가 후속 분기를 차단하는 trap), 트리거 시점·식별 신호의 부재처럼 LLM 상식으로 메울 수 없거나 적용 시 실행 결과가 실제로 달라지는 운영성 결함은 수용한다.

- **Do:** 권고가 자연어 정의를 객관 풀로 풀어내는 식이면 일단 기각 후보로 분류
- **Don't:** "더 명확하니까 수용"으로 무비판 수용 — 본문이 비대해지는 비용을 함께 평가

## 사유 작성 기준

각 처분에 **1줄 사유**를 붙인다. 사유는 다음 중 하나의 형태여야 한다:

- 수용: "X 위험이 실재함" / "테스트 커버리지 공백 인정"
- 기각: "지적한 함수는 시스템 경계 밖이라 입력 검증 불필요" / "제안 패턴은 이 프로젝트 컨벤션과 충돌"
- 유보: "별도 PR로 분리 — 현 작업 범위 초과" / "사용자 결정 필요"

- **Do:** 구체적 근거(파일·함수·맥락) 포함
- **Don't:** "동의함" / "맞는 말" / "나중에" 같은 비검증성 사유

## 출력 분기

여기서 "워크스페이스"는 일부 스킬이 사이클 산출물을 저장하는 `_workspace/` 디렉토리를 가리킨다. 디렉토리가 현재 작업 트리에 존재하면 워크스페이스 모드로 간주한다.

### 기본: 응답 본문 표

리뷰 결과를 받은 직후 응답에 다음 표를 포함한다.

```markdown
## 리뷰 처분

| # | 지적 (요약) | 처분 | 사유 |
|---|------------|------|------|
| 1 | 토큰 만료 검증 누락 | 수용 | auth/token.ts:42 위험 실재, 즉시 수정 |
| 2 | 함수명 camelCase 통일 | 기각 | 프로젝트 컨벤션은 snake_case |
| 3 | 통합 테스트 추가 권고 | 유보 | 별도 태스크로 분리 |
```

### 워크스페이스 존재 시: 파일에도 append

`_workspace/` 디렉토리가 존재하는 워크플로우 안에서는 위 표를 응답에도 출력하고 **동시에** `_workspace/_review_disposition.md`에 append 한다. 파일이 없으면 신규 생성.

```markdown
## YYYY-MM-DD HH:MM — <리뷰어 이름> (<대상 요약>)

| # | 지적 (요약) | 처분 | 사유 |
|---|------------|------|------|
| ... |
```

- **Do:** 동일 사이클 내 여러 리뷰가 발생하면 각 리뷰마다 새 섹션 추가
- **Don't:** 기존 섹션 덮어쓰기 (이력 보존 필요)

## 처분 후 후속 행동

- **수용** 항목은 같은 응답 또는 다음 도구 호출에서 실제 수정으로 이어져야 한다. 표에만 "수용"으로 적고 코드를 안 고치는 것은 금지.
- **기각** 비율이 한 리뷰에서 **지적 4건 이상 + 기각 50% 초과**일 때 사용자에게 1문장으로 알린다 (예: "리뷰 6건 중 4건 기각 — 사유는 표 참조"). 분모 하한을 두는 이유는 1/2·2/3 같은 trivial 비율로 알림이 발화되는 것을 막기 위함. 사용자가 심판 호출 여부를 결정할 수 있게 함.
- **유보** 항목은 `tasks/` 또는 사용자에게 위임한다. 표에만 남기고 잊혀지는 것을 막는다.

## 적용 면제

- 사용자가 명시적으로 "표 생략", "처분 기록 없이" 등을 지시한 경우
- 리뷰 결과가 단일 ✅(이슈 0건)
- 리뷰어가 아닌 일반 서브에이전트(예: `Explore`, `Plan`)의 결과
- 오케스트레이션 중·대 자동 흐름의 `code-reviewer`·`security-reviewer` 결과 — 리뷰어가 차단 비트와 처분 권고를 산출하고 메인은 비트로 라우팅하므로 메인의 본문 판정·처분 표 작성을 면제한다 (소 빠른 경로의 메인 직접 처분과 `prompt-reviewer` 처분은 면제 대상 아님)
