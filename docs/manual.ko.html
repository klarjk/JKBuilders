1. /dev-loop 계열 — 멀티세션 개발 지휘

큰 기능을 여러 세션에 걸쳐 개발할 때 쓰는 중심 워크플로우입니다. 계획을 세우고, 설계를 결정하고, 구현·테스트·리뷰까지 한 흐름으로 굴립니다.

가장 간단하게 · /dev-loop 뒤에 만들고 싶은 것을 한 문장으로 적어 실행하면 됩니다. 예: /dev-loop 사용자 프로필 편집 기능을 추가해줘. 그러면 나머지는 알아서 합니다 — 할 일 전체를 작업 흐름도로 그린 뒤, 조사할 것을 조사하고, 설계 결정을 내리고, 구현·리뷰까지 순서대로 굴립니다.

이렇게 진행됩니다

/dev · 작업 흐름도 작성→ 지금 할 수 있는 작업 골라내기→ 작업별 위임 (/adr · /impl · 조사)→ /dev-loop · 완료까지 자동 반복
  • /dev — 대화형으로 개발 계획서(DEV_PLAN)를 세웁니다. 할 일 전체를 작업 흐름도로 그린 뒤, 준비가 끝난 작업부터 실행합니다.
  • /dev-loop — 위 실행 루프를 계획이 끝날 때까지 자동 반복합니다. 흐름도의 칸을 격리된 별도 세션에 하나씩 맡기고, 되돌릴 수 없는 조작과 디자인만 사용자 화면에 남깁니다.
  • /impl — 신규 기능·리팩토링 한 건을 받아 설계→계획→구현→리뷰 에이전트 체인을 자동으로 굴립니다.
  • /adr — 아키텍처 결정을 문서로 남깁니다. 쉬운 결정은 직접, 어려운 결정은 설계+비평 수렴 에이전트로 넘깁니다.

/dev — 할 일을 '작업 흐름도'로 배치합니다

예전에는 할 일을 세션 순서대로 한 줄로 늘어놓았습니다. 지금은 플로우차트로 그립니다. 작업 하나하나가 흐름도의 칸(노드)이 되고, 칸끼리는 "무엇이 끝나야 이걸 시작할 수 있는가"로 이어집니다. 계획서에는 이 그림과 함께, 실행 판단에 쓰는 작업 목록 표가 같이 실립니다.

N1 조사 ─┐
         ├─→ N3 구현 ─→ N5 배포
N2 연구 ─┘        ↑
   └→ ◇ 형식이 다른가? ─(다름)→ N4 변환 추가 ┘

이렇게 그리면 세 가지가 자연스럽게 따라옵니다.

  • 동시에 할 수 있는 일은 동시에 — 앞선 조건이 같은 작업들은 한꺼번에 굴립니다.
  • 결과에 따라 길이 갈립니다 — 마름모(◇)는 판단 지점입니다. 확인해 보고 선택되지 않은 쪽 작업은 '건너뜀'으로 처리돼 계획이 깔끔하게 닫힙니다.
  • 모르는 것은 앞으로 당겨집니다 — 외부 규격·실측값처럼 "해봐야 아는 것"은 구현 앞의 별도 칸으로 세웁니다. 구현 도중에 막혀서 되돌아오는 일을 줄이기 위해서입니다.

작업의 여섯 가지 종류

종류어떤 일인가누가 하나
조사자료를 모아 정리하면 끝나는 일 (외부 API 규격, 라이브러리 최신 사용법)서브에이전트
연구직접 돌려봐야 결론이 나는 일 (실측·실험). 결과가 흐름을 가릅니다메인
설계아키텍처 결정 → /adr 호출메인
디자인시안은 사용자가 고르고, 메인이 그것을 구현용 사양서로 정리합니다사용자 + 메인
구현코드 작성 → /impl 호출서브에이전트
실행되돌리기 어려운 1회성 조작 (데이터 이관, 갈래 합치기, 배포). 백업·복구 경로를 먼저 확인합니다메인

사람 눈으로만 확인되는 일(육안 대조·실환경 확인·시안 선택)은 자동으로 '사용자' 몫이 되고, 다른 팀·다른 프로젝트가 해야 하는 일은 '외부' 몫으로 표시된 뒤 대기 상태로 남습니다.

구현을 동시에 굴릴 때

구현 작업 두 개를 나란히 놓으려면 두 조건을 모두 만족해야 합니다 — ① 각자 건드릴 파일이 겹치지 않고, ② 각자의 테스트가 같은 포트·같은 DB 파일·같은 외부 서비스를 동시에 잡지 않아야 합니다. 하나라도 확신이 없으면 그냥 차례대로 굴립니다.

  • 동시에 굴릴 때는 각 구현이 격리된 작업 공간(worktree)에서 자기 브랜치에만 커밋합니다.
  • 끝단 검증(e2e)은 각자 하지 않습니다. 뒤에 합치는 작업을 따로 두어 거기서 브랜치를 순서대로 합치고, 전체 테스트를 한 번 돌린 뒤, e2e도 합쳐진 상태에서 한 번만 돌립니다.
  • e2e가 실패하면 실패한 화면·기능이 닿는 파일을 작업 목록의 '담당 파일'과 대조해 원인 작업을 지목하고 그것만 다시 돌립니다. 대조로 특정되지 않으면 임의로 지목하지 않고 사용자에게 보고합니다.

/dev-loop — 칸 하나를 통째로 다른 세션에 맡깁니다

/dev는 무거운 작업 하나를 마치면 멈추고, 사용자가 /clear 후 다시 부르는 것을 전제합니다. /dev-loop는 그 재호출을 대신 돌려줍니다 — 흐름도의 칸 하나를 별도 Claude 세션에 통째로 넘기고, 계획서가 끝날 때까지 이 위임을 반복합니다. 넘긴 세션은 별도 프로세스라 대화 용량이 완전히 격리됩니다.

두 종류의 세션

세션어디서 도나하는 일하지 않는 일
메인사용자와 붙어 있는 이 화면칸 고르기·위임·회수·판정, 계획서 갱신·커밋, 되돌릴 수 없는 조작과 디자인 확정위임한 칸의 구현
작업칸 1개당 세션 1개(tmux)자기 격리 작업 공간 안에서 구현·커밋·보고계획서 쓰기(읽기 전용), 작업 공간 밖 수정
메인 · 다음 칸 선택→ 작업 세션 생성 · 위임→ 보고 회수 · 검증→ 머지 · 계획서 갱신→ 다음 칸

메인이 직접 쥐는 칸은 둘뿐입니다. ① 되돌릴 수 없는 실행(배포·데이터 이관·병렬 칸 합류) — 작업 세션은 승인 프롬프트 없이 실행하므로 제동할 사람이 없습니다. ② 주체가 사용자인 디자인 — 작업 세션에는 시안을 고를 사람이 없습니다. 나머지(조사·연구·설계·구현)는 모두 위임합니다.

작업 세션은 언제나 격리된 작업 공간에서 돕니다 · 한 칸만 돌릴 때도 워크트리를 따로 만듭니다 — 메인과 같은 트리를 쓰면 커밋이 서로 잠금을 다투기 때문입니다. 완료 판정은 산출물·커밋이 실재하고 보고의 검증 결과가 통과일 때만 내립니다. 답신 개수로는 판정하지 않습니다 — 한 세션에 여러 건을 보내면 답신이 하나로 합쳐집니다.

동시에 굴리기

실행 가능한 칸이 여럿이면 조건에 맞는 것끼리 최대 3개까지 동시에 굴립니다. 조건은 두 가지 모두입니다 — ① 각자 건드릴 파일이 겹치지 않고, ② 각자의 테스트가 같은 포트·같은 DB 파일·같은 외부 서비스를 동시에 잡지 않아야 합니다. 하나라도 확신이 없으면 차례대로 굴립니다.

구현 칸을 2개 이상 동시에 띄우려면, 그 칸들을 모두 선행으로 삼는 합치는 칸이 계획서에 있어야 합니다. 없으면 메인이 계획서에 그 칸을 먼저 추가하고 시작합니다. 도는 작업 세션 화면은 scripts/dev-view.sh가 분할 창에 비춰 줍니다 — 읽기 전용 미러라 뷰어가 실패해도 위임은 그대로 진행됩니다.

어디서 멈추나

대화 용량은 메인 세션 기준으로 셉니다. 이번 호출에서 위임한 칸 12개 또는 메인이 직접 처리한 칸 3개에 도달하면, 계획서를 갱신·커밋한 뒤 멈추고 안내합니다. 새 화면에서 /dev-loop --resume <계획서 경로>로 이어가면 됩니다.

막히면 어떻게 되나

  • 세션 위임 실패(작업 공간 생성 거부·세션 미등록·재촉해도 진전 없음) → 1회 재시도 후, 그래도 실패하면 그 칸만 메인이 직접 처리합니다(구현이면 /impl, 그 외면 /dev). 격리는 포기하되 진행은 멈추지 않습니다.
  • 머지 충돌 → 멈추고 사용자에게 보고합니다. 해소한 뒤 그 칸의 머지부터 재개합니다.
  • 정리 → 멈추거나 끝내기 전에 이번 호출로 만든 세션과 작업 공간을 확인해, 머지된 것은 거두고 미커밋·미머지로 남은 것은 경로와 사유를 보고합니다.

/impl — 작업 크기에 맞춰 워크플로우가 자동으로 달라집니다

impl은 요청을 받으면 먼저 작업 규모를 판정하고, 크기에 맞는 에이전트 구성을 스스로 정합니다. 작은 일에 무거운 절차를 씌우지 않고, 큰 일에는 설계·검증을 촘촘히 붙입니다.

크기대략 기준자동 구성 워크플로우
소파일 1~2개·함수 몇 개, 새 구조 없음메인이 직접 구현 → code-reviewer
중
(검증 생략)		파일 3~10개인데 끝단 e2e가 불필요하거나 불가능직접 계획 → tdd-guide(단위·통합) → code-reviewer
중
(검증 포함)		파일 3~10개, 웹 플로우 e2e 검증이 의미 있음planner → tdd-guide → code-reviewer → 통합 → evaluator → e2e-runner
대파일 10개+·새 모듈/패키지·외부 의존 추가architect 또는 synthesizer(설계) → planner(ultra) → tdd-guide → code-reviewer → 통합 → evaluator → e2e-runner
  • 대 규모는 계획을 ultra 모드로 세웁니다 — planner가 만든 계획을 3명의 검토자가 나눠 스스로 비평·보강합니다(중 이하에는 미적용).
  • 독립적인 작업 갈래가 2개 이상이면 자동 병렬 — 각 갈래를 격리된 작업 공간(worktree)에서 동시에 굴립니다.
  • 대 규모 설계 단계는 변경 범위로 갈립니다 — 새 첫 구현이거나 모듈 경계가 두루 바뀌면 synthesizer, 기존 모듈 내부만 바뀌면 architect.
  • 크기가 애매하면 큰 쪽으로 분류합니다.

작업(트랙)마다 성격에 맞는 테스트 방식도 자동으로 정합니다.

방식언제어떻게
선행 (BDD)결제·정산·금액·인증·권한테스트를 먼저 써서 실패를 확인(RED) → 구현(GREEN) → 리팩토링
사후핵심 사용자 여정에 닿거나 위험 로직(잔액·재고·포인트 등 상태 누적, 반올림·날짜·경계 계산)구현 먼저 → 정상 경로 + 틀리기 쉬운 경계를 테스트로 커버
생략단순 전달·표시·설정·배선테스트 없이 구현만

근거가 애매하면 '사후'가 기본입니다. 병렬 트랙이 여러 개면 각 트랙마다 따로 판정하고, 결제·인증 등 '선행' 작업은 가장 강한 모델로 고정해 다룹니다.

e2e 검증 주의 · 기본 검증 에이전트 e2e-runner는 Playwright 기반 웹 환경 전용입니다. 대상이 웹이 아니거나(모바일·CLI·데스크톱·순수 라이브러리) Playwright·전용 e2e 에이전트가 없으면 e2e 단계를 자동으로 건너뜁니다. 웹이 아닌 프로젝트에서 끝단 검증까지 원하면, 그 실행 환경에 맞는 검증 서브에이전트를 .claude/agents/e2e-*.md로 직접 작성해 두어야 합니다.

/adr — 설계 난이도에 따라 갈립니다

/adr은 결정의 난이도를 네 축(되돌리기 어려움 · 경쟁 대안 유무 · 영향 범위 · 실패/보안 민감도)으로 훑어 진행 방식을 정합니다.

  • 네 축 모두 낮음 (국소적·되돌리기 쉬움) → architect 설계 원칙만 참고해 메인이 직접 ADR을 작성합니다.
  • 하나라도 뚜렷함 → synthesizer 하나가 architect와 critic을 내부에서 붙여 적대적 검증·수렴을 거친 뒤 ADR을 도출합니다.
  • 애매하면 검증 쪽으로 기웁니다 — ADR은 태생이 무거운 산출물이기 때문입니다.

4. 기타 — 조건부 규칙 트리거

triggers_CLAUDE.md는 예시 템플릿입니다. rules-detail/의 규칙들은 자동으로 로드되지 않으므로, Claude가 특정 작업 전에 해당 규칙을 읽도록 하려면 이 파일의 "조건부 상세 규칙" 섹션을 본인의 전역 ~/.claude/CLAUDE.md에 복사해 넣습니다.

  • claude-doc-writing-rules — Claude가 읽는 문서(CLAUDE.md·SKILL.md·agents 등)를 작성·수정할 때
  • learnings-memory-rules — 세션 중 외부 사실을 검증했을 때
  • review-disposition-rules — 리뷰어 에이전트 결과를 처리하기 전

설치 방법

이 저장소는 Claude Code 자체를 위한 것이라, 설치도 클로드에게 맡기면 됩니다. 내려받은 뒤 본인의 Claude에게 아래처럼 부탁하세요.

전체 이식

이 JKBuilders 저장소의 워크플로우를 내 Claude Code 시스템에 이식해줘.
agents/ · commands/ · skills/ · rules/ · rules-detail/ · scripts/ 를 내
~/.claude/ 아래 대응 위치에 복사하고, triggers_CLAUDE.md 의 트리거 정의를
내 전역 ~/.claude/CLAUDE.md 에 병합해줘. 겹치는 항목이 있으면 먼저 알려줘.

계열만 골라 이식 (예: /dev-loop 계열만)

JKBuilders의 /dev-loop 계열만 내 시스템에 이식해줘.
skills/dev · dev-loop · impl · adr · tdd-workflow 와 이들이 스폰하는
agents/* , 그리고 rules/ · rules-detail/ · scripts/ 를 ~/.claude/ 아래에 설치하고,
triggers_CLAUDE.md 의 트리거를 내 전역 CLAUDE.md 에 병합해줘.
설치 후 '필수 설정' 항목을 순서대로 안내해줘.
설치 전 확인 · 각 에이전트 앞머리에 model: opus / sonnet / fable 지정이 있습니다. 본인 요금제에서 못 쓰는 모델이면 조정이 필요합니다. 또 파일들은 ~/.claude/ 경로 관례를 전제하므로, 다른 위치에 설치하면 참조 경로도 함께 바꿔야 합니다.

필수 설정 — settings.json

이 워크플로우는 서브에이전트 스폰 · 병렬 트랙 · 중첩 수렴을 전제로 합니다. ~/.claude/settings.json에 아래 세 항목을 반드시 설정해야 합니다.

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "worktree": { "baseRef": "head" },
  "statusLine": {
    "type": "command",
    "command": "python3 ~/.claude/scripts/status-writer.py"
  }
}
  • CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS — 필수. 이 플래그가 없으면 중첩 서브스폰(서브에이전트가 다시 다른 서브에이전트를 스폰)이 원천적으로 불가능합니다. /impl의 에이전트 체인과 synthesizer의 architect·critic 수렴이 이 위에서만 동작하므로, 꺼져 있으면 해당 단계가 실패합니다.
  • worktree.baseRef — 필수. impl의 병렬 트랙이 격리 작업 공간(worktree)을 만들 때 기준 커밋입니다.
  • statusLine — /dev 계열을 쓴다면 필수. 화면 장식이 아니라 계측 배선입니다. 세션이 자기 대화 용량을 재는 재료가 ~/.claude/status/<세션ID>.json이고, 이 파일을 만드는 것은 클로드가 아니라 사용자의 상태줄 명령입니다. 없으면 세션이 자기 포화를 못 재고, 못 재면 정지·인수인계 시점을 놓칩니다.
이미 쓰는 상태줄이 있다면 · 위 명령으로 덮어쓰지 마세요. scripts/status-writer.py 머리말의 ②번 방식대로, 쓰던 스크립트 맨 앞(표준입력을 읽기 전)에 네 줄만 얹으면 됩니다. 표준입력을 대신 읽어 기록하고 같은 내용을 되돌려 놓으므로 기존 상태줄은 평소대로 돕니다.

선택 설정 — tmux

/dev-loop는 칸을 맡을 작업 세션을 tmux로 띄웁니다. tmux가 없으면 스폰 전 검사에서 멈춥니다. /dev·/impl 단독 사용에는 필요 없습니다.
