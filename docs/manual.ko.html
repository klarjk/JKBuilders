1. /dev-loop 계열 — 멀티세션 개발 지휘

큰 기능을 여러 세션에 걸쳐 개발할 때 쓰는 중심 워크플로우입니다. 계획을 세우고, 설계를 결정하고, 구현·테스트·리뷰까지 한 흐름으로 굴립니다.

가장 간단하게 · /dev-loop 뒤에 만들고 싶은 것을 한 문장으로 적어 실행하면 됩니다. 예: /dev-loop 사용자 프로필 편집 기능을 추가해줘. 그러면 나머지는 알아서 합니다 — 할 일 전체를 작업 흐름도로 그린 뒤, 조사할 것을 조사하고, 설계 결정을 내리고, 구현·리뷰까지 순서대로 굴립니다. 계획이 길어 대화 용량이 차도 사용자가 다시 부를 필요가 없습니다 — 안에서 세션을 갈아 끼우며 끝까지 갑니다.

이렇게 진행됩니다

/dev · 작업 흐름도 작성→ 지금 할 수 있는 작업 골라내기→ 작업별 위임 (/adr · /impl · 조사)→ /dev-loop · 완료까지 자동 반복
  • /dev — 대화형으로 개발 계획서(DEV_PLAN)를 세웁니다. 할 일 전체를 작업 흐름도로 그린 뒤, 준비가 끝난 작업부터 실행합니다.
  • /dev-loop — 위 실행 루프를 계획이 끝날 때까지 자동 반복합니다. 세션을 창구·지휘·작업 세 층으로 나눠 흐름도의 칸을 격리된 별도 세션에 하나씩 맡기고, 되돌릴 수 없는 조작과 디자인만 사람에게 되돌립니다. 쌓인 후속 작업 소진(--followup)도 같은 구조로 굴립니다.
  • /impl — 신규 기능·리팩토링 한 건을 받아 설계→계획→구현→리뷰 에이전트 체인을 자동으로 굴립니다.
  • /adr — 아키텍처 결정을 문서로 남깁니다. 쉬운 결정은 직접, 어려운 결정은 설계+비평 수렴 에이전트로 넘깁니다.

/dev — 할 일을 '작업 흐름도'로 배치합니다

예전에는 할 일을 세션 순서대로 한 줄로 늘어놓았습니다. 지금은 플로우차트로 그립니다. 작업 하나하나가 흐름도의 칸(노드)이 되고, 칸끼리는 "무엇이 끝나야 이걸 시작할 수 있는가"로 이어집니다. 계획서에는 이 그림과 함께, 실행 판단에 쓰는 작업 목록 표가 같이 실립니다.

N1 조사 ─┐
         ├─→ N3 구현 ─→ N5 배포
N2 연구 ─┘        ↑
   └→ ◇ 형식이 다른가? ─(다름)→ N4 변환 추가 ┘

칸 번호는 실제로는 계획서 번호를 앞에 붙인 007-N1 꼴입니다. 계획서가 여러 개 열려 있어도 세션 이름·작업 갈래 이름이 섞이지 않게 하기 위해서입니다.

이렇게 그리면 세 가지가 자연스럽게 따라옵니다.

  • 동시에 할 수 있는 일은 동시에 — 앞선 조건이 같은 작업들은 한꺼번에 굴립니다.
  • 결과에 따라 길이 갈립니다 — 마름모(◇)는 판단 지점입니다. 확인해 보고 선택되지 않은 쪽 작업은 '건너뜀'으로 처리돼 계획이 깔끔하게 닫힙니다.
  • 모르는 것은 앞으로 당겨집니다 — 외부 규격·실측값처럼 "해봐야 아는 것"은 구현 앞의 별도 칸으로 세웁니다. 구현 도중에 막혀서 되돌아오는 일을 줄이기 위해서입니다.

사람 눈으로만 확인되는 일(육안 대조·실환경 확인·시안 선택)은 자동으로 '사용자' 몫이 되고, 다른 팀·다른 프로젝트가 해야 하는 일은 '외부' 몫으로 표시된 뒤 대기 상태로 남습니다.

구현을 동시에 굴릴 때

구현 작업 두 개를 나란히 놓으려면 두 조건을 모두 만족해야 합니다 — ① 각자 건드릴 파일이 겹치지 않고, ② 각자의 테스트가 같은 포트·같은 DB 파일·같은 외부 서비스를 동시에 잡지 않아야 합니다. 하나라도 확신이 없으면 그냥 차례대로 굴립니다.

  • 동시에 굴릴 때는 각 구현이 격리된 작업 공간(worktree)에서 자기 브랜치에만 커밋합니다.
  • 끝단 검증(e2e)은 각자 하지 않습니다. 뒤에 합치는 작업을 따로 두어 거기서 브랜치를 순서대로 합치고, 전체 테스트를 한 번 돌린 뒤, e2e도 합쳐진 상태에서 한 번만 돌립니다.
  • e2e가 실패하면 실패한 화면·기능이 닿는 파일을 작업 목록의 '담당 파일'과 대조해 원인 작업을 지목하고 그것만 다시 돌립니다. 대조로 특정되지 않으면 임의로 지목하지 않고 사용자에게 보고합니다.

계획서에 낱말 사전을 답니다

계획서에는 용어 절이 붙습니다. 같은 것을 두 이름으로 부르고 있던 낱말, 사용자의 업무 용어·조어, 코드 이름과 한국어 호칭이 짝인 것 — 이 셋만 등재합니다. 지휘는 대화 용량이 차면 교체되고 작업 세션은 칸마다 새로 나기 때문에, 여기 적어두지 않은 낱말은 세션마다 새로 지어집니다.

사용자가 쓴 낱말이 이깁니다. 사용자가 같은 대상을 계획서와 다른 말로 부르면, 되묻지 않고 계획서의 표제어를 그 말로 갈아 끼웁니다. 반대로 서브에이전트가 지정된 용어를 안 쓰고 다른 말을 지어 오면, 용어 절은 그대로 두고 반영할 문장만 정규 용어로 고칩니다.

쌓인 후속 작업 소진하기

개발이 진행되면 계획서마다 "나중에 할 것"이 쌓입니다. /dev --followup(자동·병렬로 끝까지 돌리려면 /dev-loop --followup)은 여러 계획서에 흩어진 후속·유보 항목을 전부 걷어 한 대장으로 모은 뒤, 묶음 단위로 소진합니다.

걷은 항목은 코드와 대조해 다섯 가지를 판정합니다 — 이미 반영·폐기됐는지, 어떤 성격인지, 어느 파일에 착지하는지, 무엇에 의존하는지, 그리고 필수인지 아닌지입니다. 그다음 사용자에게 세 번 묻습니다.

  • 무효·중복 항목 — 닫아도 되는지 승인받고 출처 계획서에서 닫습니다.
  • 비필수 항목 — 겉동작이 그대로인 정돈, 취향 수준의 개선, 체감되지 않는 성능 다듬기 등을 한 질문으로 묶어 보여주고, 승인하면 이번 판에서 빼 유보로 내립니다(지우지 않습니다). 결함 수정과 기능에 영향을 주는 것은 판정이 갈려도 필수로 남습니다.
  • 새 기능 항목 — 항목 하나씩 승인을 받고, 승인된 것만 이번 판에 넣습니다.

/dev-loop — 세 층으로 나눠 계획 끝까지 굴립니다

/dev는 무거운 작업 하나를 마치면 멈추고, 사용자가 /clear 후 다시 부르는 것을 전제합니다. /dev-loop는 그 재호출까지 대신합니다 — 세션을 창구·지휘·작업 세 층으로 나눠, 흐름도의 칸을 별도 Claude 세션에 하나씩 넘기고 계획서가 끝날 때까지 반복합니다. 각 세션은 별도 프로세스라 대화 용량이 완전히 격리됩니다.

핵심은 창구입니다. 창구는 지휘가 쓰는 대화 용량을 수치로 지켜보다가, 가득 차기 전에 새 지휘로 갈아 끼웁니다. 그래서 계획이 아무리 길어도 대화 한도에 걸려 멈추지 않습니다. 프로젝트마다 창구가 따로 서므로 한 대의 기계에서 여러 저장소를 동시에 돌릴 수 있습니다.

지휘가 직접 하지 않고 사람에게 되돌리는 칸은 둘뿐입니다. ① 되돌릴 수 없는 실행(배포·데이터 이관) ② 주체가 사용자인 디자인. 무인 지휘는 이 둘을 집행하지 않고 '사람 대기'로 올립니다. 그 밖의 실행 칸(병렬 칸 합류 등)은 지휘가 직접 처리하되 한 회차에 하나까지입니다 — 직접 처리는 위임보다 대화 용량을 세 배 가까이 먹기 때문입니다. 나머지(조사·연구·설계·구현)는 모두 위임합니다.

작업 세션은 언제나 격리된 작업 공간에서 돕니다 · 한 칸만 돌릴 때도 워크트리를 따로 만듭니다 — 지휘와 같은 트리를 쓰면 커밋이 서로 잠금을 다투기 때문입니다. 완료 판정은 산출물·커밋이 실재하고 보고의 검증 결과가 통과일 때만 내립니다. 답신 개수로는 판정하지 않습니다 — 한 세션에 여러 건을 보내면 답신이 하나로 합쳐집니다.

— 그냥 입력하면 이 라운드가 끝날 때까지 큐에 머뭅니다.

Esc를 한 번 누른 뒤 지시하면 그 자리에서 받습니다. 그냥 타이핑하면 이번 회차가 끝날 때까지 입력이 대기합니다. 끼어들어도 감시 상태는 잃지 않고, 지시를 처리한 뒤 같은 조건으로 감시를 다시 엽니다.

어디서 사람을 부르나

정상 운전에서 사용자에게 판단을 청하는 자리는 셋뿐입니다.

  • 되돌릴 수 없는 조작과 디자인 시안 — 지휘가 집행하지 않고 올립니다.
  • 지휘를 세 번째로 갈아 끼울 때 — "여기까지 왔는데 계속할까요"를 묻고, 답을 받기 전에는 다음 지휘를 띄우지 않습니다. 그 뒤로는 교체할 때마다 묻습니다.
  • 막혔을 때 — 지휘가 응답을 잃거나 진전이 없으면 창구가 상황과 기록 경로를 실어 보고합니다.

멈추지 않습니다 — 갈아 끼웁니다

예전에는 위임한 칸 수를 세어 일정 개수에서 멈추고 사용자가 새 화면에서 다시 불러야 했습니다. 지금은 개수 예산이 없습니다. 정지 판단은 지휘의 대화 용량 수치가 하고, 용량이 차면 창구가 새 지휘를 띄워 인수인계합니다. 인수인계 재료는 계획서 자체이므로, 지휘는 칸을 위임하기 직전에도 진행 상태를 계획서에 적고 커밋해 둡니다 — 교체는 예고 없이 오고, 커밋되지 않은 판단은 함께 사라지기 때문입니다.

무인으로 도는 동안 지시가 서로 어긋나거나 시킨 대로 했는데 결과가 다르면, 각 세션이 그 자리에서 한 줄짜리 결함 기록을 남기고 하던 일을 계속합니다. 쌓인 기록은 다음 개시 첫머리와 판이 끝나는 자리에서 건수로 보고되고, scripts/dl-incident.sh --tally로 내용을 봅니다.

동시에 굴리기

실행 가능한 칸이 여럿이면 조건에 맞는 것끼리 최대 3개까지 동시에 굴립니다. 조건은 두 가지 모두입니다 — ① 각자 건드릴 파일이 겹치지 않고, ② 각자의 테스트가 같은 포트·같은 DB 파일·같은 외부 서비스를 동시에 잡지 않아야 합니다. 하나라도 확신이 없으면 차례대로 굴립니다.

구현 칸을 2개 이상 동시에 띄우려면, 그 칸들을 모두 선행으로 삼는 합치는 칸이 계획서에 있어야 합니다. 없으면 지휘가 계획서에 그 칸을 먼저 추가하고 시작합니다. 도는 작업 세션 화면은 scripts/dev-view.sh가 분할 창에 비춰 줍니다 — 읽기 전용 미러라 뷰어가 실패해도 위임은 그대로 진행됩니다.

겹치지 않게 하는 제약

제약내용
저장소당 한 판같은 저장소에 이미 판이 열려 있으면 두 번째 개시를 거부합니다. 다른 저장소끼리는 얼마든지 동시에 돕니다
기계당 채널 한 자리채널 모드는 기계 전체에서 한 프로젝트만 쓸 수 있습니다. 자리가 차 있으면 개시가 막히는 대신 화면 모드로 내려옵니다
동시 작업 세션 3개한 지휘가 동시에 띄우는 작업 세션의 상한입니다

막히면 어떻게 되나

  • 세션 위임 실패(작업 공간 생성 거부·세션 미등록·재촉해도 진전 없음) → 1회 재시도 후, 그래도 실패하면 그 칸만 지휘가 직접 처리합니다(구현이면 /impl, 그 외면 /dev). 격리는 포기하되 진행은 멈추지 않고, 결함 기록을 한 줄 남깁니다.
  • 합칠 때 충돌 → 지휘가 먼저 해소를 시도하고, 풀 수 없을 때만 사용자에게 되돌립니다.
  • 정리 → 판을 끝내기 전에 이번에 만든 세션과 작업 공간을 확인해, 합쳐진 것은 거두고 미커밋·미합류로 남은 것은 경로와 사유를 보고합니다.

/impl — 작업 크기에 맞춰 워크플로우가 자동으로 달라집니다

impl은 요청을 받으면 먼저 작업 규모를 판정하고, 크기에 맞는 에이전트 구성을 스스로 정합니다. 작은 일에 무거운 절차를 씌우지 않고, 큰 일에는 설계·검증을 촘촘히 붙입니다.

크기대략 기준자동 구성 워크플로우
소파일 1~2개·함수 몇 개, 새 구조 없음메인이 직접 구현 → code-reviewer
중
(검증 생략)		파일 3~10개인데 끝단 e2e가 불필요하거나 불가능직접 계획 → tdd-guide(단위·통합) → code-reviewer
중
(검증 포함)		파일 3~10개, 웹 플로우 e2e 검증이 의미 있음planner → tdd-guide → code-reviewer → 통합 → evaluator → e2e-runner
대파일 10개+·새 모듈/패키지·외부 의존 추가architect 또는 synthesizer(설계) → planner(ultra) → tdd-guide → code-reviewer → 통합 → evaluator → e2e-runner
  • 대 규모는 계획을 ultra 모드로 세웁니다 — planner가 만든 계획을 3명의 검토자가 나눠 스스로 비평·보강합니다(중 이하에는 미적용).
  • 독립적인 작업 갈래가 2개 이상이면 자동 병렬 — 각 갈래를 격리된 작업 공간(worktree)에서 동시에 굴립니다.
  • 대 규모 설계 단계는 변경 범위로 갈립니다 — 새 첫 구현이거나 모듈 경계가 두루 바뀌면 synthesizer, 기존 모듈 내부만 바뀌면 architect.
  • 크기가 애매하면 큰 쪽으로 분류합니다.

작업(트랙)마다 성격에 맞는 테스트 방식도 자동으로 정합니다.

방식언제어떻게
선행 (BDD)결제·정산·금액·인증·권한테스트를 먼저 써서 실패를 확인(RED) → 구현(GREEN) → 리팩토링
사후핵심 사용자 여정에 닿거나 위험 로직(잔액·재고·포인트 등 상태 누적, 반올림·날짜·경계 계산)구현 먼저 → 정상 경로 + 틀리기 쉬운 경계를 테스트로 커버
생략단순 전달·표시·설정·배선테스트 없이 구현만

근거가 애매하면 '사후'가 기본입니다. 병렬 트랙이 여러 개면 각 트랙마다 따로 판정하고, 결제·인증 등 '선행' 작업은 가장 강한 모델로 고정해 다룹니다.

e2e 검증 주의 · 기본 검증 에이전트 e2e-runner는 Playwright 기반 웹 환경 전용입니다. 대상이 웹이 아니거나(모바일·CLI·데스크톱·순수 라이브러리) Playwright·전용 e2e 에이전트가 없으면 e2e 단계를 자동으로 건너뜁니다. 웹이 아닌 프로젝트에서 끝단 검증까지 원하면, 그 실행 환경에 맞는 검증 서브에이전트를 .claude/agents/e2e-*.md로 직접 작성해 두어야 합니다.

/adr — 설계 난이도에 따라 갈립니다

/adr은 결정의 난이도를 네 축(되돌리기 어려움 · 경쟁 대안 유무 · 영향 범위 · 실패/보안 민감도)으로 훑어 진행 방식을 정합니다.

  • 네 축 모두 낮음 (국소적·되돌리기 쉬움) → architect 설계 원칙만 참고해 메인이 직접 ADR을 작성합니다.
  • 하나라도 뚜렷함 → synthesizer 하나가 architect와 critic을 내부에서 붙여 적대적 검증·수렴을 거친 뒤 ADR을 도출합니다.
  • 애매하면 검증 쪽으로 기웁니다 — ADR은 태생이 무거운 산출물이기 때문입니다.

  • claude-doc-writing-rules — Claude가 읽는 문서(CLAUDE.md·SKILL.md·agents 등)를 작성·수정할 때
  • learnings-memory-rules — 세션 중 외부 사실을 검증했을 때
  • review-disposition-rules — 리뷰어 에이전트 결과를 처리하기 전

설치 방법

이 저장소는 Claude Code 자체를 위한 것이라, 설치도 클로드에게 맡기면 됩니다. 내려받은 뒤 본인의 Claude에게 아래처럼 부탁하세요.

전체 이식

이 JKBuilders 저장소의 워크플로우를 내 Claude Code 시스템에 이식해줘.
agents/ · commands/ · skills/ · rules/ · rules-detail/ · scripts/ 를 내
~/.claude/ 아래 대응 위치에 복사하고, triggers_CLAUDE.md 의 트리거 정의를
내 전역 ~/.claude/CLAUDE.md 에 병합해줘. 겹치는 항목이 있으면 먼저 알려줘.

계열만 골라 이식 (예: /dev-loop 계열만)

JKBuilders의 /dev-loop 계열만 내 시스템에 이식해줘.
skills/dev · dev-loop · impl · adr · tdd-workflow 와 이들이 스폰하는
agents/* , 그리고 rules/ · rules-detail/ · scripts/ 를 ~/.claude/ 아래에 설치하고,
triggers_CLAUDE.md 의 트리거를 내 전역 CLAUDE.md 에 병합해줘.
설치 후 '필수 설정' 항목을 순서대로 안내해줘.
설치 전 확인 · 각 에이전트 앞머리에 model: opus / sonnet / fable 지정이 있습니다. 본인 요금제에서 못 쓰는 모델이면 조정이 필요합니다. 또 파일들은 ~/.claude/ 경로 관례를 전제하므로, 다른 위치에 설치하면 참조 경로도 함께 바꿔야 합니다.

필수 설정 — settings.json

이 워크플로우는 서브에이전트 스폰 · 병렬 트랙 · 중첩 수렴을 전제로 합니다. ~/.claude/settings.json에 아래 세 항목을 반드시 설정해야 합니다.

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "worktree": { "baseRef": "head" },
  "statusLine": {
    "type": "command",
    "command": "python3 ~/.claude/scripts/status-writer.py"
  }
}
  • CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS — 필수. 이 플래그가 없으면 중첩 서브스폰(서브에이전트가 다시 다른 서브에이전트를 스폰)이 원천적으로 불가능합니다. /impl의 에이전트 체인과 synthesizer의 architect·critic 수렴이 이 위에서만 동작하므로, 꺼져 있으면 해당 단계가 실패합니다.
  • worktree.baseRef — 필수. impl의 병렬 트랙이 격리 작업 공간(worktree)을 만들 때 기준 커밋입니다.
  • statusLine — /dev 계열을 쓴다면 필수. 화면 장식이 아니라 계측 배선입니다. 세션이 자기 대화 용량을 재는 재료가 ~/.claude/status/<세션ID>.json이고, 이 파일을 만드는 것은 클로드가 아니라 사용자의 상태줄 명령입니다. /dev-loop에서는 더 결정적입니다 — 창구가 지휘의 이 파일을 읽어 언제 갈아 끼울지 판단하므로, 없으면 교체 판정 자체가 서지 않아 무인 완주가 성립하지 않습니다.
이미 쓰는 상태줄이 있다면 · 위 명령으로 덮어쓰지 마세요. scripts/status-writer.py 머리말의 ②번 방식대로, 쓰던 스크립트 맨 앞(표준입력을 읽기 전)에 네 줄만 얹으면 됩니다. 표준입력을 대신 읽어 기록하고 같은 내용을 되돌려 놓으므로 기존 상태줄은 평소대로 돕니다.

필수 설정 — /dev-loop을 쓴다면

  • tmux — 지휘 세션과 작업 세션이 모두 tmux 위에서 돕니다. 없으면 세션이 서지 않습니다. /dev·/impl 단독 사용에는 필요 없습니다.
  • jq — 무인 운전 중 쌓인 결함 기록을 세는 데 씁니다(scripts/dl-incident.sh). 없으면 그 집계만 빈손이 되고 루프 자체는 돕니다.
  • 프로젝트 신뢰 수락 — 무인 세션은 Claude Code가 처음 띄우는 "이 폴더를 신뢰하느냐" 확인 창을 넘지 못합니다. /dev-loop은 띄우기 전에 이 수락 여부를 확인하고, 없으면 스폰하지 않고 사용자에게 넘깁니다. 대상 프로젝트에서 claude를 한 번 직접 실행해 수락해 두세요.
채널 모드는 이 배포본에 없습니다 · /dev-loop은 원래 진행 상황을 텔레그램으로 주고받을 수 있지만, 그 통로는 공식 플러그인에서 갈라져 나온 외부 코드라 여기 싣지 않았습니다. 설치 후에는 항상 화면 모드로 돌며, 개시할 때마다 그 사실을 알리는 경고가 한 줄 뜹니다 — 정상 동작입니다.
