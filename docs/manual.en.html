JKBuilders Manual

A development workflow collection for Claude Code — one command sets multiple specialist agents collaborating behind the scenes. This document focuses on how you use it and what to watch out for.

At a glance

Four families. Each starts from a single entry command and pulls in the agents it needs on its own.

/dev-loop family

Multi-session dev orchestration. Lays the work out as a flowchart and loops to completion. Three-tier sessions + Telegram remote control.

/dev · /dev-loop · /impl · /adr

/prp family

A one-shot pipeline from requirements → plan → implementation → PR.

/prp-prd · /prp-plan · /prp-implement · /prp-pr

Memory family

Skills/agents remember what they learned for the next run.

/add-memory

Other

Conditional rule-trigger examples, etc.

triggers_CLAUDE.md

1. /dev-loop family — multi-session orchestration

The core workflow for building a large feature across multiple sessions. It plans, decides the design, and runs implementation, testing, and review in one flow.

Simplest way · Just run /dev-loop followed by one sentence describing what you want to build. e.g. /dev-loop add a user profile editing feature. It takes care of the rest — draws the whole job as a work flowchart, researches what it needs, makes the design decisions, and runs build and review in order.

How it flows

/dev · draw the work flowchart→ pick what's ready to run→ delegate per task (/adr · /impl · research)→ /dev-loop · auto-repeat to done
  • /dev — Builds a development plan (DEV_PLAN) interactively. It lays the whole job out as a work flowchart, then runs whichever tasks have their prerequisites met.
  • /dev-loop — Auto-repeats that execution loop until the plan is complete. The orchestrating role moves into its own session that gets swapped out when it fills up, and each task is handed to an isolated session.
  • /impl — Takes one feature or refactor and runs the design → plan → build → review agent chain automatically.
  • /adr — Records an architecture decision. Easy calls are handled directly; hard ones go to a design + critique convergence agent.

/dev — the work is laid out as a flowchart

It used to line the work up as a single sequence of sessions. Now it draws a flowchart. Each task becomes one box (a node), and boxes are connected by "what has to finish before this can start". The plan file carries that picture alongside a task table, which is what execution decisions actually read from.

N1 research ─┐
             ├─→ N3 build ─→ N5 deploy
N2 experiment┘        ↑
   └→ ◇ format differs? ─(yes)→ N4 add conversion ┘

Three things follow naturally from drawing it this way.

  • Whatever can run at once, runs at once — tasks sharing the same prerequisites go together.
  • The path can fork on a result — a diamond (◇) is a decision point. Once it's settled, the branch not taken is marked skipped, so the plan can still close cleanly.
  • Unknowns are pulled to the front — anything you only learn by checking (external formats, measured values) becomes its own box ahead of the build, instead of stalling the build halfway through.

The six kinds of task

KindWhat it isWho does it
ResearchDone once the material is gathered and written up (external API contracts, current library usage)Sub-agent
ExperimentOnly settled by actually running it. The result decides which way the flow goesMain
DesignArchitecture decisions → calls /adrMain
Visual designYou pick the mockup; main turns it into a build-ready specYou + main
BuildWriting code → calls /implSub-agent
OperationOne-shot, hard-to-undo actions (data migration, merging branches, deploys). Backup and rollback paths are checked firstMain

Anything only a human can confirm (eyeballing a result, checking a real environment, choosing a mockup) is assigned to you automatically, and anything another team or project owns is marked external and left waiting.

Running builds side by side

Two build tasks can run in parallel only if both hold — ① the files they touch don't overlap, and ② their tests don't grab the same port, DB file, or external service at the same time. If either is uncertain, they run one after another instead.

  • When they do run in parallel, each build works in an isolated worktree and commits only to its own branch.
  • End-to-end verification is not run per branch. A separate merge task sits behind them: it merges the branches in order, runs the full test suite once, then runs e2e once on the combined tree.
  • If e2e fails, the failing flow's files are matched against the "owned files" column to pin down which build caused it, and only that one re-runs. If the match is inconclusive, it reports to you rather than guessing.

/dev-loop — it swaps sessions out and keeps going

/dev stops after one heavy task and expects you to /clear and call it again. /dev-loop does that re-calling for you. But the session running the loop fills up too. So the orchestrating role is moved off your screen into its own session, and when that session fills up it is replaced wholesale.

Three tiers

TierWhere it runsWhat it ownsWhat it doesn't
CounterThe screen you're talking toSpawning, replacing, and relaying for the commander. The initial planning session when no plan exists yetTask judgment, delegation/collection, plan updates
CommanderOne separate terminal session (tmux)Delegating, collecting, judging tasks; updating and committing the plan; measuring its own contextReplacing itself, irreversible operations
WorkerOne session per task (tmux)Building and committing inside its own isolated workspace, then reportingWriting the plan (read-only), edits outside its workspace
Counter · confirm plan→ spawn commander→ delegate · collect→ counter swaps a full commander→ done

The counter doesn't judge, and the commander doesn't pretend it won't die. The moment the counter starts reading into the plan it fills up at the same rate, and splitting the tiers stops meaning anything. So the counter passes the commander's words to you verbatim and your answer back verbatim — no summarizing, no adjudicating.

Replacement is not resumption · At the soft limit the commander stops sending out new work, collects only what is in flight, wraps up, and asks to be replaced. At the hard limit it gives up collecting too, records progress, and leaves. The counter kills that session and spawns a brand-new one — resuming the same session would restore the whole conversation and relieve nothing. Instead the handover is banked into the plan continuously, so whenever it is cut off the next commander picks up from the plan alone.

The limits are measured in absolute tokens, not percentages — soft at 200,000, hard at 300,000. Cutting well short of a one-million-token window is a cost and judgment-quality decision, not a capacity one. The measurement happens at two points — right before new work is sent out, and right after a Telegram answer lands — and the verdict is a numeric comparison, not a model judgment.

It runs while you're away — Telegram

Nobody sits in front of the commander. Anything printed to its screen reaches no one. So whatever needs a human is carried out over Telegram by the postman (skills/postman/).

  • Sessions know nothing about Telegram — they only write files into their own mailbox. The postman reads them, sends them out, and injects your reply straight into that session's screen.
  • Questions with choices go out as inline buttons. Pressing one types that label into the session. Pressing the same button twice still executes once.
  • Everything outbound passes a single masking gate — secret-shaped values, secret-shaped names, and the contents of any file registered in never_send are stripped.
  • Irreversible actions can't be unlocked by a button either. What a human reads remotely is a truncated summary, and approving a deploy or a data migration off a summary throws away the point of the gate.
The postman is optional · /dev-loop runs fine without it — questions just appear on screen only, and you have to be at the desk. See Optional setup — Telegram below for installation and tokens.

Running things in parallel

When several tasks are ready, the eligible ones run up to three at a time. Eligibility needs both conditions — ① the files each will touch don't overlap, and ② their tests don't grab the same port, the same DB file, or the same external service at once. If either is uncertain, they run sequentially.

To run two or more build tasks at once, the plan must contain a join task whose prerequisites are all of them. If it doesn't, the commander adds that box to the plan first and then starts.

Clearing the backlog — --followup

Development keeps pushing "things to fix later" outside the plan. /dev-loop --followup gathers those loose ends into a follow-up ledger and clears it in parallel through the same three tiers.

  • Harvesting, triage, and grouping happen at the counter — every item needs your approval, and there is nowhere but the screen you're on to do that.
  • Clearing happens at the commander. All the counter hands over is the ledger path and the approved scope — two lines.
  • Follow-up items have almost no ordering dependencies and are already split by the files they land in, so they parallelize better than plan nodes — three at a time by default, four when they're light.

Feature additions found outside the approved scope are not built; they're recorded as "held" in the ledger and reported together when the run ends. Approval is handled by the triage step of the next --followup call.

What happens when something jams

  • Worker delegation fails → retried once; if it still fails, the commander handles that one task directly. Isolation is given up, progress isn't.
  • Commander spawn fails → retried once with an ordinary (heavier) configuration. If that fails too, the counter doubles as the commander and drives the loop itself (giving up the unbounded loop).
  • Two consecutive replacements for the same reason → there is no third. It tells you and stops, so a cause that replacement can't fix — a broken measurement wire, say — doesn't spin the replacement loop.

/impl — the workflow adapts automatically to the size of the work

impl first judges the scale of the request, then picks an agent setup to match. It won't wrap a tiny change in heavy process, and it layers design and verification thickly onto big ones.

SizeRough criteriaAuto-composed workflow
Small1–2 files, a few functions, no new structuremain implements directly → code-reviewer
Medium
(no verify)		3–10 files, but end-to-end e2e is unneeded or impossibleplan directly → tdd-guide (unit & integration) → code-reviewer
Medium
(with verify)		3–10 files, web-flow e2e verification is meaningfulplanner → tdd-guide → code-reviewer → integration → evaluator → e2e-runner
Large10+ files, new module/package, external dependencyarchitect or synthesizer (design) → planner (ultra) → tdd-guide → code-reviewer → integration → evaluator → e2e-runner
  • Large jobs plan in ultra mode — the plan planner produces is split among three reviewers who critique and harden it themselves (not applied below Large).
  • Two or more independent work tracks run in parallel automatically — each in its own isolated workspace (worktree).
  • The Large design step depends on change scope — a first-time build or broad boundary changes use synthesizer; internal-only changes to an existing module use architect.
  • If the size is ambiguous, it classifies up.

Each job (track) also gets a testing approach chosen to fit its nature.

ApproachWhenHow
Test-first (BDD)payments, settlement, money, auth, permissionswrite the test first and watch it fail (RED) → implement (GREEN) → refactor
Test-aftercore user journeys or risky logic (accumulating state like balance/stock/points; boundary math like rounding/dates)implement first → cover the happy path plus the error-prone edges with tests
Skipsimple pass-through, display, config, wiringimplement only, no tests

When unclear, "test-after" is the default. With multiple parallel tracks each is judged separately, and test-first work (payments, auth) is pinned to the strongest model.

e2e caveat · The default verification agent e2e-runner is for Playwright-based web environments only. If the target isn't web (mobile, CLI, desktop, a pure library) or Playwright / a dedicated e2e agent is absent, the e2e step is skipped automatically. To get end-to-end verification on a non-web project, you must author a verification sub-agent matching that runtime yourself as .claude/agents/e2e-*.md.

/adr — it branches by design difficulty

/adr scans a decision's difficulty across four axes (hard to reverse · competing alternatives · blast radius · failure/security sensitivity) to decide how to proceed.

  • All four low (local, easily reversible) → the main agent writes the ADR directly, consulting only architect's design principles.
  • Any one pronounced → a single synthesizer pairs architect with critic internally for adversarial review and convergence, then derives the ADR.
  • When ambiguous, it leans toward verification — an ADR is a heavyweight artifact by nature.

2. /prp family — one-shot pipeline

A pipeline based on the PRP (Product Requirement Prompt) methodology, running from a requirements doc all the way to a PR. All of it is adapted from Wirasm/PRPs-agentic-eng.

/prp-prd · define requirements→ /prp-plan · implementation plan→ /prp-implement · execute→ /prp-pr · open PR
CommandRole
/prp-prdGenerate a problem-first, hypothesis-driven product spec (PRD) interactively
/prp-planBuild an implementation plan via codebase analysis and pattern extraction
/prp-implementExecute the plan through validation loops
/prp-prOpen a GitHub PR from unpushed commits on the current branch

Watch out · This family writes artifacts to .claude/PRPs/ (prds · plans · reports). /prp-pr requires the GitHub CLI (gh).

4. Other — conditional rule triggers

triggers_CLAUDE.md is an example template. The rules under rules-detail/ are not auto-loaded, so to make Claude read a rule before a given task, copy this file's "conditional detailed rules" section into your global ~/.claude/CLAUDE.md.

  • claude-doc-writing-rules — when writing/editing docs Claude reads (CLAUDE.md · SKILL.md · agents, etc.)
  • learnings-memory-rules — when you've verified an external fact during a session
  • review-disposition-rules — before handling a reviewer agent's results

Before installing · Each agent's frontmatter pins a model: opus / sonnet / fable. If your plan can't access that model, adjust it. The files also assume the ~/.claude/ path convention — install elsewhere and you must update the reference paths too.

Required settings — settings.json

This workflow assumes sub-agent spawning · parallel tracks · nested convergence. The three settings below in ~/.claude/settings.json are required.

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "worktree": { "baseRef": "head" },
  "statusLine": {
    "type": "command",
    "command": "python3 ~/.claude/scripts/status-writer.py"
  }
}
  • CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS — Required. Without this flag, nested sub-spawning (a sub-agent spawning yet another sub-agent) is impossible. /impl's agent chain and synthesizer's architect·critic convergence only work on top of it, so those steps fail when it's off.
  • worktree.baseRef — Required. The base commit used when impl's parallel tracks create isolated workspaces (worktrees).
  • statusLine — Required if you use /dev-loop. Not decoration but instrumentation. The only source the commander has for measuring its own context is ~/.claude/status/<session-id>.json, and that file is written by your status line command, not by Claude. Without it the commander can't see itself fill up, and a commander that can't see that misses its swap point.
Already running your own status line? · Don't overwrite it with the command above. Use method ② described in the header of scripts/status-writer.py: four lines at the very top of your existing script (before it reads stdin). It reads stdin on your script's behalf, records it, and puts it back, so your status line keeps working as before.

Optional setup — Telegram (the postman)

Connect the postman to keep the loop running while you're away from the desk. /dev-loop runs fine without it — questions just appear on screen only, and you have to be there.

  1. Create a bot. Send /newbot to @BotFather on Telegram; once you pick a name and username it hands you a single token line.
  2. Put the token in a file, nowhere else. The default location is ~/.claude/dev-run/telegram-bot-token; point POSTMAN_TOKEN_FILE elsewhere if you prefer. 
    mkdir -p ~/.claude/dev-run
install -m 600 /dev/null ~/.claude/dev-run/telegram-bot-token
# open it in an editor and paste the single token line
    Don't use echo — the token would sit in your shell history.
  3. Look up your own user id. Send your bot any 1:1 message, then run the snippet below to see from.id. 
    python3 -c "import urllib.request,json,pathlib; \
  t=pathlib.Path.home().joinpath('.claude/dev-run/telegram-bot-token').read_text().strip(); \
  print(json.load(urllib.request.urlopen('https://api.telegram.org/bot'+t+'/getUpdates')))"
  4. Create the config at mode 600 first, then fill it in with an editor — an editor creating it from scratch leaves it at 644. 
    install -m 600 /dev/null ~/.claude/postman/config.json
    {
  "allowed_user_ids": [123456789],
  "chat_id": 123456789,
  "never_send": ["~/private-notes.md"]
}
  5. Verify. Sweeps config, permissions, and token in one pass; touches no network. Fix and re-run if it prints even one warning — the exit code is 0 even with warnings, so read the count on the last line to judge a pass. 
    python3 ~/.claude/skills/postman/postman/bot.py --check
Two security musts
· Don't leave never_send empty. The postman captures session screens and sends them to Telegram. Register the paths of any plaintext personal files here so their contents can't ride out in a capture.
· An empty allowed_user_ids discards every incoming update. That's the safe default, but launching with it empty looks exactly like a silently dead channel.

The postman is one per machine, one project at a time — a Telegram bot has exactly one receiver, so two projects running at once intercept each other's messages. It's only needed while a dev loop is running, so it isn't registered as an always-on service and retires itself when the commander has been absent for a while. Full protocol and file layout live in skills/postman/README.md.

Optional setup — tmux

/dev-loop launches its commander and worker sessions through tmux. Without tmux it stops at the pre-spawn check. /dev and /impl on their own don't need it.
